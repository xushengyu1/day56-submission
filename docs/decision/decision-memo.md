## 背景

本项目为校园场景的 AI 失物招领匹配与认领复核 Web 系统，两天三人 MVP。PRD V0.6 已确认以下技术约束：

- **后端**：Python + FastAPI
- **数据库**：PostgreSQL + pgvector 扩展
- **AI 边界**：只用文本 AI，不训练模型，不做图像识别
- **数据分类**：PUBLIC / MATCH_ONLY / VERIFICATION / PRIVATE 四级

宋姿毅、徐胜宇确认了以下技术选型，覆盖 PRD 中已确认的部分：

| 组件 | 用户确认选择 |
|---|---|
| 前端框架 | React 18 + Vite |
| Embedding 模型 | Qwen3.7plus |
| 核验 AI | Qwen3.7plus |
| 匹配流程 | 双方向量化 → pgvector 相似度 → TOP-5 |
| 隐藏问题 | 拾得者上传隐藏特征 → LLM 自动生成问题 |

## 方案对比

### 三个方案的加权评分

| 方案 | 总分 | 核心优势 | 核心劣势 |
|---|---:|---|---|
| **A：向量匹配 + LLM 核验** | **4.15** | 语义匹配最强；LLM 自动生成问题；React 体验最佳 | 外部 API 依赖 |
| B：规则优先 + 最小 AI | 3.60 | 2 天可交付性最高 | 前端体验差；问题质量参差不齐 |
| C：LLM 驱动全流程 | 3.55 | 语义理解最深 | 2 天交付风险最高 |

详细评分见 `docs/options/tradeoff-matrix.md`。

---

## 后果

### 正面影响

1. **匹配质量最高**：Qwen3.7plus 双方信息均向量化，语义召回能力强
2. **拾得者门槛最低**：只需上传隐藏特征，LLM 自动生成规范问题
3. **核验准确**：Qwen3.7plus 能识别同义表达和模糊描述
4. **前端体验最佳**：React SPA 组件化交互
5. **架构清晰**：前后端分离，各层职责明确

### 负面影响 / 代价与风险

1. **外部 API 依赖**：Qwen3.7plus 均需网络可达
2. **React 开发成本**：Vite + JWT + CORS 联调高于 SSR
3. **LLM 问题生成不稳定**：同一特征可能生成不同问题
4. **拾得者控制力降低**：问题由 LLM 生成而非手动编写

### 风险缓解措施

| 风险 | 缓解措施 |
|---|---|
| API 不可用 | 预置 fallback 结果 + 降级为关键词/规则匹配 |
| LLM 问题质量差 | 标准 prompt 模板 + 拾得者确认机制 |
| React 联调时间不足 | 核心页面优先；管理员页面可简化 |
| 阈值不合理 | 边界样例验证；答辩时说明 Demo 局限 |

## V4 受控多模态决策（当前版本 — 完整重写）

# 决策：采用受控多模态与分类型认领核验

- 日期：2026-07-16
- 状态：**已接受**（旧 V3 决策已被替代；V4 方案 A 已接受）
- 决策者：宋姿毅
- PRD 基线：V0.8（已确认）

## 背景

原 V3 方案基于文本向量候选和其他物品隐藏特征核验，并明确图片不进入 AI。用户随后新增：物品分为身份证件类和其他；拾得者上传图片后由多模态模型提取名称与特征且可修改；身份证件无需隐藏特征，改由失主输入完整证件号码精确核验；公开信息必须掩码。

这项变更使原"图片只展示"和"统一隐藏核验"决策失效，需要重新选择图片处理、隐私保护和双流程架构。

## 决策

采用方案 A：

1. 拾得者原图按 PRIVATE 上传到 FastAPI；
2. 多模态模型生成类型、名称、公开特征和可选证件字段草稿；
3. 拾得者修改并确认，只有确认后的文本进入候选和向量；
4. 身份证件生成掩码、脱敏副本和号码 HMAC，失主输入完整号码后做精确比较；
5. 其他物品由拾得者填写隐藏特征，继续使用 LLM 问题生成和回答核验；
6. 模型失败时降级为手工填写，自动核验异常时转管理员；
7. 两条路径通过后都进入待交接，最终已认领由拾得者确认。

本决策已由用户确认。模型 spike、编码和运行测试属于后续验证，不作为本次决策已发生的前提条件。

## 方案对比

| 方案 | 加权分 | 关键优势 | 主要问题 |
|---|---:|---|---|
| A：受控多模态 + 人工确认 + 分类型核验 | **4.40** | 完整覆盖需求；号码确定性核验；失败可降级 | 双数据版本和双流程增加实现量 |
| B：OCR/规则优先 | 4.00 | 隐私强、最可测试 | 不满足普通物品自动名称/特征提取 |
| C：端到端多模态 LLM | 3.25 | 接口统一、表面代码少 | 敏感数据暴露、概率判断、难复现 |

评分依据和敏感性分析见 `../options/tradeoff-matrix.md`。

## 后果

### 正面影响

- 满足用户新增的多模态发布辅助需求。
- 身份证件号码匹配由确定性代码完成，不依赖 LLM 猜测。
- 拾得者确认使 AI 错误可见、可改、可追溯。
- 证件号码、原图、公开副本和候选文本用途分离。
- 外部 API 失败不会阻断手工发布和管理员兜底。

### 负面影响/代价与风险

- 需要实现 PRIVATE 原图与 PUBLIC 脱敏副本。
- 新增证件类型、号码规范化、HMAC、尝试限制和异常复核。
- 多模态 API 会接触 PRIVATE 图片，需要明确授权和供应商风险。
- 通用图片理解模型未承诺证件号码零错误，必须保留人工确认。
- 双流程扩大测试矩阵；两天内必须限制证件类型和图片能力。

## 风险缓解

1. 首版仅支持居民身份证。
2. 使用合成/脱敏测试图片，不使用真实个人数据。
3. 完整号码不进 LLM、向量、普通日志或候选 DTO。
4. 应用层 HMAC-SHA256；密钥从环境注入，不写仓库。
5. 多模态结果经 Pydantic 校验并由拾得者确认。
6. 模型超时、非法结构和脱敏失败都有手工降级。
