## 最终选择

**选择方案 A：向量匹配 + LLM 核验**

在 Python + FastAPI + PostgreSQL + pgvector 已确认的前提下，用户确认采用：

- **前端**：React 18 + Vite
- **数据访问**：SQLAlchemy ORM + raw SQL for pgvector
- **认证**：JWT (access + refresh)
- **Embedding**：text-embedding-v4（双方信息均向量化）
- **匹配引擎**：pgvector 余弦相似度 + 时间/地点规则评分 → TOP-5
- **隐藏问题生成**：mimoV2.5-pro（拾得者上传隐藏特征 → LLM 自动生成问题）
- **回答核验**：mimoV2.5-pro（语义比对回答与隐藏特征）

---

## 选择理由

### 核心判断：向量匹配 + LLM 核验是最优组合

1. **匹配质量最高**：text-embedding-v4 双方信息均向量化，pgvector 余弦相似度语义召回 TOP-5
2. **拾得者门槛最低**：只需上传隐藏特征，LLM 自动生成规范的开放式问题
3. **核验准确**：mimoV2.5-pro 语义比对，能识别同义表达和模糊描述
4. **前端体验最佳**：React SPA 组件化交互，候选展示/问答/状态管理体验最佳
5. **架构清晰**：前后端分离，各层职责明确

### 为什么不选方案 B（规则优先 + 最小 AI）

- 前端交互体验差（SSR + 整页刷新）
- 拾得者手动编写问题学习成本高、质量参差不齐
- Embedding 和核验模型与用户选择不符

### 为什么不选方案 C（LLM 驱动全流程）

- 匹配延迟过高（每次匹配需调用 LLM）
- LLM 输出不稳定，难以断言测试
- 无法利用已确认的 pgvector 能力

# 最终建议

**文档版本：** V4.1  
**决策日期：** 2026-07-16  
**建议状态：** 已接受  
**历史状态：** design_option.md V3.0 已被新需求触发重新评审，不再直接进入实现

## 1. 建议选择

建议选择 **方案 A：受控多模态 + 人工确认 + 分类型核验**。

核心不是让多模态模型决定所有权，而是把 AI 放在最适合的位置：

1. 图片上传后提取物品类型、名称和公开特征草稿；
2. 拾得者修改并确认，避免模型错误变成正式事实；
3. 身份证件用确定性证件号码精确比对；
4. 其他物品使用文本向量候选和隐藏特征 LLM 核验；
5. 两条路径都只进入待交接，最终交接由拾得者确认。

## 2. 建议的最小技术组合

| 组件 | 建议 | 状态 |
|---|---|---|
| 前端 | React 18 + Vite；增加图片预览、AI 草稿编辑、证件脱敏确认和双核验页面 | 已确认 |
| 后端 | FastAPI + Pydantic | 固定约束 |
| 数据层 | PostgreSQL + pgvector；MVP 小数据使用精确余弦检索 | 已确认 |
| 多模态提取 | MiMo-V2.5 图片理解 API，通过适配器调用 | 待 spike 验证 |
| 文本 embedding | text-embedding-v4 | 已确认 |
| 其他物品核验 | mimoV2.5-pro 文本能力 | 已确认，运行效果待验证 |
| 证件号码 | 应用层规范化 + HMAC-SHA256 + 常量时间比较 | 已确认 |
| 图片 | PRIVATE 原图 + PUBLIC 脱敏副本；失主图片不进多模态 | 已确认 |
| 认证 | JWT；号码尝试次数绑定用户和候选 | 已确认 |

## 3. 为什么推荐 A

1. **最符合新 PRD**：完整覆盖自动提取、人工修改、身份证件和其他物品双路径。
2. **把概率问题与确定问题分开**：名称/特征可由 AI 建议，证件号码最终匹配必须由确定性代码完成。
3. **可形成可信证据链**：原图引用、AI 草稿、人工修改、HMAC 比对结果和状态变化都有记录。
4. **失败可降级**：多模态 API 不可用时允许手工填写，不丢失图片和草稿。
5. **两天仍有收口可能**：不做视觉相似度、模型训练、多证件 OCR 适配或独立向量库。

取舍矩阵结果：A **4.40**，B **4.00**，C **3.25**。详见 `docs/options/tradeoff-matrix.md`。

## 4. 接受该方案的代价

1. 比旧 V3 多出图片双版本、AI 草稿确认和身份证件状态分支。
2. PRIVATE 图片要发送外部模型时必须有明确提示、访问控制和审计。
3. 通用多模态模型可能读错证件号码，不能取消拾得者确认。
4. 需要 HMAC 密钥管理；密钥丢失或变更会影响历史号码匹配。
5. 双流程使单元、集成和 E2E 用例数量增加。

## 5. 建议的 MVP 收缩

为保证两天交付，建议确认以下限制：

1. 身份证件类首版只支持居民身份证。
2. 失主可选图片只做 PRIVATE 支持材料，不调用多模态模型。
3. 证件候选展示固定掩码文本；自动脱敏失败时不展示图片。
4. 每个账号对同一证件候选最多尝试 2 次。
5. 多模态失败允许拾得者手工填写。
6. pgvector 使用精确搜索，不建立 HNSW/IVFFlat。

## 6. 实现与验收前的必要条件

1. 将 Q1～Q15 的确认答案写成接口约束、状态机断言和测试用例。
2. 使用合成证件图片完成最小多模态 spike，验证结构化输出可用且可修正。
3. 验证演示环境可获得 MiMo API Key；否则启用 mock + 手工降级并在 README 说明。
4. 测试与演示不使用真实身份证件号码和真实个人图片。
