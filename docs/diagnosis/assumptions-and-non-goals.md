# 假设与非目标

| 类型 | 内容 | 原因 |
|---|---|---|
| 假设 | 项目根目录确定为 `E:\A-xiaomi\xiaomi\2\day6` | 用户明确要求所有交付写入该目录 |
| 假设 | 最少实现服务端 + Web 前端两个技术端 | 用户明确基础要求；普通用户/管理员是同一前端中的角色视图 |
| 假设 | 使用不含真实个人信息的模拟失物/招领数据 | 作业允许模拟数据，且更适合稳定复现边界样例 |
| 假设 | 候选匹配 AI 只处理公开文本；回答核验 AI 在隔离流程中比较拾得者标准答案与失主回答 | 两个 AI 阶段必须分开，候选解释不得泄露标准答案 |
| 假设 | 候选匹配分只用于 Top 5 排序；普通物品按关键问题逐题结果路由，不再计算综合认领可信度 | 公开相似度不能作为隐藏答案正确性的二次证据 |
| 假设 | 单个 Web 应用承载失主、拾得者、管理员三种角色视图 | 符合“端”和“角色”的定义，服务端是另一个技术端 |
| 假设 | 后端采用 Python + FastAPI，业务数据库采用 PostgreSQL + pgvector | 用户在 PRD 第四次迭代中用 PostgreSQL 替代 MySQL，并明确需要同时存储结构化与向量数据 |
| 假设 | 候选公开描述使用 AI embedding 向量相似度计 50 分，颜色与其它公开外观不再独立计分 | 用户在 PRD 第五次迭代中明确这些内容属于同一语义证据，需要避免重复加分 |
| 假设 | 前端采用 React + Vite，服务端采用 FastAPI，PostgreSQL + pgvector 保存结构化数据和公开文本向量，JWT 负责基础认证 | 已在方案 A 和详细设计 V1.3 中确认；真实依赖版本与运行效果仍待验证 |
| 假设 | 普通物品拾得者至少填写一段能生成 2～3 个开放式问题的隐藏描述 | 没有有效核验基准时系统无法安全发布；不足时只能保存草稿 |
| 非目标 | 学校统一认证、短信验证、找回密码和第三方登录 | MVP 实现基础注册登录，但不实现生产账号体系 |
| 非目标 | 短信/邮件/微信通知、物流与线上签收 | MVP 仅在核验通过后展示拾得者联系方式，线下交接后由拾得者确认 |
| 非目标 | 图片真伪鉴定、视觉相似度认领和失主图片多模态提取 | 多模态只为拾得者生成可修改的发布草稿，不能作为所有权证据 |
| 非目标 | 跨校、多租户和独立大规模向量数据库 | MVP 使用 PostgreSQL pgvector 完成小规模文本向量存储与相似度检索，不部署额外向量服务 |
| 非目标 | AI 自动标记实际交接完成或作法律物权裁决 | 普通物品核验通过或身份证精确匹配只能进入待交接，最终已认领由拾得者确认 |
| 非目标 | 完整申诉、仲裁和复杂撤回系统 | MVP 只实现 `UNMATCHED` 与 `CLAIM_REVIEW` 两类主动复核；多人认领是管理员 P0 异常场景 |
| 非目标 | 追求大量页面和视觉特效 | 评分重点是判断、取舍、验证和证据链 |

主动收窄范围、写清「两天内不做什么」是加分项，不是减分项。
