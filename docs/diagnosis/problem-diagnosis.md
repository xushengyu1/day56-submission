# 问题诊断

- **题目表面要求**：读入失物/招领记录，AI 生成候选、理由、不一致点和可信程度；用户发起认领；管理员依据未公开特征确认或驳回。
- **我们认为真正问题**：在同类物品高度相似、描述模糊且验证细节不能公开的情况下，如何提高候选发现效率，又不把"相似"误当"归属"。系统需要分离公开候选分与隐藏核验分，让高可信申请自动进入待交接、异常申请转统一管理员，并把实际交接确认保留给持有实物的拾得者。
- **目标用户**：发布失物并认领的失主；发布招领、保管并交付实物的拾得者；处理异常认领的统一管理员。
- **关键利益相关方**：失主、拾得者、管理员、评委/审计者。AI 是系统能力，不是角色。
- **核心矛盾**：①匹配召回率 vs 冒领风险；②解释充分 vs 隐藏答案泄露；③高可信自动流转效率 vs AI 误放行风险；④公开整体图片的辨识价值 vs 暴露隐藏特征；⑤完整留痕 vs 敏感信息最小化。
- **约束条件**：两天；至少服务端 + 一个前端/客户端；允许模拟数据但必须说明；六类 AI 工作至少五类有真实记录；至少两条 AI 建议被拒绝/修改；至少一条 E2E 和三个自拟边界/失败样例；过程证据与个人贡献可追溯。
- **信息缺口**：三名成员的姓名与具体分工、指定技术栈/模型、是否必须现场实时调用 AI、联系方式展示是否需要拾得者二次授权、自动流转阈值是否经样例验证。
- **风险和冲突**：AI 只给正向理由造成锚定；隐藏答案经接口/提示词泄露；为了"功能完整"做太多页面；模型失败导致主流程不可演示；赛后补日志造成证据不可信。
- **非目标**：学校统一认证、短信/找回密码等生产账号能力、图像识别和图片 AI 匹配、物流/签收、大规模检索、多租户、法律意义的物权裁决、复杂申诉流程。
- **成功标准**：Web 前端与服务端真实跑通失主/拾得者输入、公开候选、隐藏问答、自动或人工路由、联系方式授权、拾得者交接确认；至少一次核心冲突规则生效；至少一个失败/边界可演示；结果能追溯输入、AI 分析、自动/人工判断和最终状态。

## 1. 问题全貌

### 1.1 题目表面要求

读入失物/招领记录，AI 生成候选、理由、不一致点和可信程度；用户发起认领；管理员依据未公开特征确认或驳回。

### 1.2 我们认为的真正问题

在校园场景中，同类物品（黑色折叠伞、AirPods、水杯等）高度相似，用户描述模糊且记忆存在偏差，而验证真实归属的隐藏细节又不能公开泄露。核心挑战是：

1. **匹配效率 vs 冒领风险**：公开信息只能说明"可能相关"，不能证明"是你的"；提高召回率会同时提高冒领窗口。
2. **解释充分 vs 答案泄露**：向用户解释候选保留原因时，如何避免把隐藏验证答案间接透露。
3. **自动流转效率 vs AI 误放行**：高可信申请自动进入待交接可减少管理员负担，但 AI 判断错误可能导致错误交接。
4. **图片辨识价值 vs 隐藏特征暴露**：整体图片帮助失主判断是否值得认领，但也可能泄露用于核验的局部特征。
5. **完整留痕 vs 敏感信息最小化**：审计需要完整证据链，但不能让管理员或接口过度暴露 PRIVATE 数据。

### 1.3 目标用户

| 角色 | 定义 | 核心任务 |
|---|---|---|
| 失主 | 丢失物品并希望找回的注册用户 | 发布失物公开信息、查看候选、回答隐藏问题、核验通过后联系拾得者 |
| 拾得者 | 拾到并实际保管物品的注册用户 | 发布招领和整体图片、上传隐藏特征、授权联系方式、线下交接并标记已认领 |
| 统一管理员 | 系统异常与争议审核的预置管理账号 | 复核非高可信、冲突、多人认领和 AI 异常申请 |

AI 是系统能力，不是用户角色。实物始终由拾得者保管。

### 1.4 关键利益相关方

失主、拾得者、管理员、评委/审计者。AI 不是利益相关方。

## 2. 核心冲突

| 冲突编号 | 冲突描述 | PRD 中的平衡策略 |
|---|---|---|
| C1 | 匹配召回率 vs 冒领风险 | 公开候选高分不能单独确认归属；必须隐藏问答核验通过才可自动待交接 |
| C2 | 解释充分 vs 答案泄露 | 候选页展示匹配点/冲突点/保留原因，但 VERIFICATION 标准答案只供核验服务和管理员 |
| C3 | 自动流转效率 vs AI 误放行 | 候选分≥80 + 隐藏核验分≥85 + 综合可信度≥85 + 无硬冲突才自动；其余转管理员 |
| C4 | 图片辨识 vs 隐藏特征暴露 | 整体图片仅供人工浏览，不进入 AI 匹配；拾得者需确认图片不含隐藏特征 |
| C5 | 留痕完整性 vs 数据最小化 | 四级分类（PUBLIC/MATCH_ONLY/VERIFICATION/PRIVATE）+ 按角色/阶段控制可见范围 |

## 5. 非目标（明确不做）

1. **学校统一身份认证** — 仅基础注册登录 + 预置管理员
2. **图像识别 / 图片 AI 匹配** — 整体图片只供人工浏览
3. **独立向量数据库** — 不引入 Milvus/Pinecone，用 pgvector
4. **训练或微调模型** — 只用外部 API
5. **复杂地图和路径推断** — 地点只做预定义层级和文本规则
6. **真实物流 / 线上签收** — 系统只提供联系方式和状态记录
7. **法律意义上的物权判定** — 自动待交接和管理员通过不等于法律证明
8. **多组织 / 多校区 / 复杂管理员协作** — 单系统统一管理员
9. **复杂申诉和追责流程** — 只保留审核结果和审计记录
10. **大规模生产部署验证** — 两天 MVP 使用模拟数据

## 1. 问题全貌

### 1.1 真正需要解决的问题

系统不是简单的"图片识别失物"工具，而是在两天 MVP 内同时证明：

1. 拾得者能够低成本发布：填写时间、地点、上传图片，AI 自动产生可修改的名称和特征草稿。
2. 系统能够按风险分流：身份证件用号码精确核验，其他物品用隐藏特征核验。
3. 敏感数据不会因 AI 接入或候选展示泄露：证件原图、完整号码、隐藏特征和联系方式按用途隔离。
4. AI 出错时有人负责确认和兜底：拾得者确认提取结果，异常申请进入管理员复核，最终交接仍由拾得者确认。
5. 所有结论可以回溯到原始输入、AI 草稿、人工修改、规则结果和最终状态。

### 1.2 用户和利益相关方

| 对象 | 目标 | 核心风险 | 系统责任 |
|---|---|---|---|
| 失主 | 快速找到并认领物品 | 冒领、号码输入泄露、错误候选 | 只显示安全候选；提供分类型核验 |
| 拾得者 | 快速发布并安全交付 | AI 识别错误、公开敏感信息、错误交接 | AI 草稿可修改；拾得者确认最终值 |
| 管理员 | 只处理异常和争议 | 看见过多敏感数据、依据不足 | 默认脱敏；查看必要证据和审计事件 |
| 答辩评审 | 验证团队判断与 AI 协作 | 只有漂亮页面、没有失败证据 | 展示两条主路径、失败降级和证据链 |
| 开发团队 | 两天内完成可运行 MVP | 模型、图片、权限和双流程超出工期 | 收缩服务数量，固定最小闭环 |

## 2. 核心冲突

| 冲突 | 两端诉求 | 当前判断 |
|---|---|---|
| 自动识别效率 vs 错误事实 | AI 自动填写越多越省事；证件号错一位就会错误核验 | AI 只生成草稿，拾得者必须修改/确认 |
| 候选可发现性 vs 证件隐私 | 展示越多越容易认出；完整号码和原图不能公开 | 只展示掩码号码与脱敏副本 |
| AI 统一流程 vs 类型差异 | 单流程实现简单；身份证件有稳定唯一号码，普通物品没有 | 采用身份证件/其他双核验分支 |
| 自动放行效率 vs 冒领风险 | 号码匹配希望直接认领；异常和试探不能放行 | 精确匹配只进入待交接；超限/多人/异常转人工 |
| 多模态能力 vs 两天交付 | 模型能提取名称、特征和号码；图片脱敏、失败降级和权限增加工作量 | 不做视觉相似度和训练，只做一次提取 + 人工确认 |
| 证据完整性 vs 敏感数据最小化 | 答辩需要可追溯；日志不能保存完整号码 | 保存摘要、掩码、模型版本、修改差异和比对结果，不保存普通日志明文 |

## 3. 约束条件

1. 周期 2 天、团队 3 人，必须优先完整闭环而不是模型准确率研究。
2. 至少包含 Web 前端和 FastAPI 服务端两个技术端。
3. PostgreSQL + pgvector、Python + FastAPI 是固定约束。
4. 拾得者必须上传图片；失主图片可选。
5. 多模态输出不得直接发布，必须保留人工确认步骤。
6. 身份证件候选不得展示完整证件号码或未脱敏原图。
7. 其他物品仍需要隐藏特征；身份证件不要求隐藏特征。
8. 号码匹配成功代表"核验通过并进入待交接"，不代表实物已经归还或法律归属确定。
9. AI/外部 API 可能超时、限流、返回非法结构或误识别，必须存在手工降级。
10. 过程材料必须严格留痕，未执行的测试不能标记为通过。

## 4. 预设假设

| 假设 | 当前默认 | 如果不成立的影响 |
|---|---|---|
| 身份证件具有可人工确认的唯一号码 | 是 | 无号码证件需改走其他物品隐藏核验 |
| 拾得者可以合法查看并确认所拾证件号码 | 是 | 需改为管理员确认或完全禁止自动核验 |
| MVP 可调用外部多模态 API | 是 | 必须准备 mock 或手工填写演示降级 |
| 证件号码可以规范化后做精确相等比较 | 是 | 若存在不同编号格式，需增加证件类型专属规范化规则 |
| 小规模候选适合 pgvector 精确检索 | 是 | 数据量扩大后才评估 HNSW/IVFFlat |
| 失主可选图片暂不参与自动提取 | 是 | 若要求参与，需新增双图片处理、权限和测试范围 |

## 5. 明确非目标

1. 不做基于图片相似度的自动所有权判断。
2. 不训练或微调视觉模型、OCR 模型或 embedding 模型。
3. 不部署独立向量数据库。
4. 不接学校统一身份认证、公安或证件真伪验证系统。
5. 不验证证件是否伪造、挂失或已失效。
6. 不在候选页公开完整姓名、证件号码、地址或未脱敏原图。
7. 不实现物流、电子签收和法律物权裁决。
8. 不证明真实校园大规模准确率。

## 7. 诊断结论

原 V3"纯文本向量 + LLM 隐藏核验"方案已不能完整覆盖新需求。新方案必须同时具备：受控多模态提取、人工确认、证件脱敏、证件号确定性比对、其他物品隐藏核验和失败降级。是否把全部判断交给多模态模型，是本轮方案比较的关键分歧。
