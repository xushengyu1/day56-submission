# 问题诊断

**文档版本：** V4.0  
**更新日期：** 2026-07-16  
**需求基线：** `prd.md` V0.8（已确认）  
**变更原因：** 新增身份证件/其他物品双类型、多模态图片提取和证件号码精确认领，原 V3 方案需要重新评审。

---

## 1. 问题全貌

### 1.1 真正需要解决的问题

系统不是简单的“图片识别失物”工具，而是在两天 MVP 内同时证明：

1. 拾得者能够低成本发布：填写时间、地点、上传图片，AI 自动产生可修改的名称和特征草稿。
2. 系统能够按风险分流：身份证件用号码精确核验，其他物品用隐藏特征核验。
3. 敏感数据不会因 AI 接入或候选展示泄露：证件原图、完整号码、隐藏特征和联系方式按用途隔离。
4. AI 出错时有人负责确认和兜底：拾得者确认提取结果，异常申请进入管理员复核，最终交接仍由拾得者确认。
5. 所有结论可以回溯到原始输入、AI 草稿、人工修改、规则结果和最终状态。

### 1.2 用户和利益相关方

| 对象 | 目标 | 核心风险 | 系统责任 |
|---|---|---|---|
| 失主 | 快速找到并认领物品 | 冒领、号码输入泄露、错误候选 | 只显示安全候选；提供分类型核验 |
| 拾得者 | 快速发布并安全交付 | AI 识别错误、公开敏感信息、错误交接 | AI 草稿可修改；拾得者确认最终值 |
| 管理员 | 只处理异常和争议 | 看见过多敏感数据、依据不足 | 默认脱敏；查看必要证据和审计事件 |
| 答辩评审 | 验证团队判断与 AI 协作 | 只有漂亮页面、没有失败证据 | 展示两条主路径、失败降级和证据链 |
| 开发团队 | 两天内完成可运行 MVP | 模型、图片、权限和双流程超出工期 | 收缩服务数量，固定最小闭环 |

## 2. 核心冲突

| 冲突 | 两端诉求 | 当前判断 |
|---|---|---|
| 自动识别效率 vs 错误事实 | AI 自动填写越多越省事；证件号错一位就会错误核验 | AI 只生成草稿，拾得者必须修改/确认 |
| 候选可发现性 vs 证件隐私 | 展示越多越容易认出；完整号码和原图不能公开 | 只展示掩码号码与脱敏副本 |
| AI 统一流程 vs 类型差异 | 单流程实现简单；身份证件有稳定唯一号码，普通物品没有 | 采用身份证件/其他双核验分支 |
| 自动放行效率 vs 冒领风险 | 号码匹配希望直接认领；异常和试探不能放行 | 精确匹配只进入待交接；超限/多人/异常转人工 |
| 多模态能力 vs 两天交付 | 模型能提取名称、特征和号码；图片脱敏、失败降级和权限增加工作量 | 不做视觉相似度和训练，只做一次提取 + 人工确认 |
| 证据完整性 vs 敏感数据最小化 | 答辩需要可追溯；日志不能保存完整号码 | 保存摘要、掩码、模型版本、修改差异和比对结果，不保存普通日志明文 |

## 3. 约束条件

1. 周期 2 天、团队 3 人，必须优先完整闭环而不是模型准确率研究。
2. 至少包含 Web 前端和 FastAPI 服务端两个技术端。
3. PostgreSQL + pgvector、Python + FastAPI 是固定约束。
4. 拾得者必须上传图片；失主图片可选。
5. 多模态输出不得直接发布，必须保留人工确认步骤。
6. 身份证件候选不得展示完整证件号码或未脱敏原图。
7. 其他物品仍需要隐藏特征；身份证件不要求隐藏特征。
8. 号码匹配成功代表“核验通过并进入待交接”，不代表实物已经归还或法律归属确定。
9. AI/外部 API 可能超时、限流、返回非法结构或误识别，必须存在手工降级。
10. 过程材料必须严格留痕，未执行的测试不能标记为通过。

## 4. 预设假设

| 假设 | 当前默认 | 如果不成立的影响 |
|---|---|---|
| 身份证件具有可人工确认的唯一号码 | 是 | 无号码证件需改走其他物品隐藏核验 |
| 拾得者可以合法查看并确认所拾证件号码 | 是 | 需改为管理员确认或完全禁止自动核验 |
| MVP 可调用外部多模态 API | 是 | 必须准备 mock 或手工填写演示降级 |
| 证件号码可以规范化后做精确相等比较 | 是 | 若存在不同编号格式，需增加证件类型专属规范化规则 |
| 小规模候选适合 pgvector 精确检索 | 是 | 数据量扩大后才评估 HNSW/IVFFlat |
| 失主可选图片暂不参与自动提取 | 是 | 若要求参与，需新增双图片处理、权限和测试范围 |

## 5. 明确非目标

1. 不做基于图片相似度的自动所有权判断。
2. 不训练或微调视觉模型、OCR 模型或 embedding 模型。
3. 不部署独立向量数据库。
4. 不接学校统一身份认证、公安或证件真伪验证系统。
5. 不验证证件是否伪造、挂失或已失效。
6. 不在候选页公开完整姓名、证件号码、地址或未脱敏原图。
7. 不实现物流、电子签收和法律物权裁决。
8. 不证明真实校园大规模准确率。

## 6. 成功标准

| 编号 | 成功标准 | 可验证证据 |
|---|---|---|
| S1 | 拾得者图片可得到结构化草稿并可修改确认 | API 响应、修改前后快照、页面录屏 |
| S2 | 身份证件和其他物品进入不同发布与认领路径 | 状态机测试、端到端用例 |
| S3 | 证件候选只展示掩码号码和脱敏图片 | DTO 字段扫描、截图、越权测试 |
| S4 | 完整号码精确匹配后进入待交接 | 正常 E2E、号码规范化测试 |
| S5 | 错误号码不泄露差异，尝试超限转人工 | 失败测试、审计日志 |
| S6 | 其他物品隐藏特征核验仍可运行 | 正向/冲突用例 |
| S7 | 多模态失败可以手工填写并继续发布 | 超时/非法结构降级测试 |
| S8 | 原始输入、AI 草稿、人工修改和最终结果可追溯 | 审计时间线和数据库快照 |

## 7. 诊断结论

原 V3“纯文本向量 + LLM 隐藏核验”方案已不能完整覆盖新需求。新方案必须同时具备：受控多模态提取、人工确认、证件脱敏、证件号确定性比对、其他物品隐藏核验和失败降级。是否把全部判断交给多模态模型，是本轮方案比较的关键分歧。
