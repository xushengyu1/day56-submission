**文档版本：** V3.0（基于 PRD V0.6 + 用户确认技术选型更新）
**更新日期：** 2026-07-16

---

## 1. 问题全貌

### 1.1 题目表面要求

读入失物/招领记录，AI 生成候选、理由、不一致点和可信程度；用户发起认领；管理员依据未公开特征确认或驳回。

### 1.2 我们认为的真正问题

在校园场景中，同类物品（黑色折叠伞、AirPods、水杯等）高度相似，用户描述模糊且记忆存在偏差，而验证真实归属的隐藏细节又不能公开泄露。核心挑战是：

1. **匹配效率 vs 冒领风险**：公开信息只能说明"可能相关"，不能证明"是你的"；提高召回率会同时提高冒领窗口。
2. **解释充分 vs 答案泄露**：向用户解释候选保留原因时，如何避免把隐藏验证答案间接透露。
3. **自动流转效率 vs AI 误放行**：高可信申请自动进入待交接可减少管理员负担，但 AI 判断错误可能导致错误交接。
4. **图片辨识价值 vs 隐藏特征暴露**：整体图片帮助失主判断是否值得认领，但也可能泄露用于核验的局部特征。
5. **完整留痕 vs 敏感信息最小化**：审计需要完整证据链，但不能让管理员或接口过度暴露 PRIVATE 数据。

### 1.3 目标用户

| 角色 | 定义 | 核心任务 |
|---|---|---|
| 失主 | 丢失物品并希望找回的注册用户 | 发布失物公开信息、查看候选、回答隐藏问题、核验通过后联系拾得者 |
| 拾得者 | 拾到并实际保管物品的注册用户 | 发布招领和整体图片、上传隐藏特征、授权联系方式、线下交接并标记已认领 |
| 统一管理员 | 系统异常与争议审核的预置管理账号 | 复核非高可信、冲突、多人认领和 AI 异常申请 |

AI 是系统能力，不是用户角色。实物始终由拾得者保管。

### 1.4 关键利益相关方

失主、拾得者、管理员、评委/审计者。AI 不是利益相关方。

## 2. 核心冲突

| 冲突编号 | 冲突描述 | PRD 中的平衡策略 |
|---|---|---|
| C1 | 匹配召回率 vs 冒领风险 | 公开候选高分不能单独确认归属；必须隐藏问答核验通过才可自动待交接 |
| C2 | 解释充分 vs 答案泄露 | 候选页展示匹配点/冲突点/保留原因，但 VERIFICATION 标准答案只供核验服务和管理员 |
| C3 | 自动流转效率 vs AI 误放行 | 候选分≥80 + 隐藏核验分≥85 + 综合可信度≥85 + 无硬冲突才自动；其余转管理员 |
| C4 | 图片辨识 vs 隐藏特征暴露 | 整体图片仅供人工浏览，不进入 AI 匹配；拾得者需确认图片不含隐藏特征 |
| C5 | 留痕完整性 vs 数据最小化 | 四级分类（PUBLIC/MATCH_ONLY/VERIFICATION/PRIVATE）+ 按角色/阶段控制可见范围 |

## 3. 约束条件

| 约束类型 | 具体约束 |
|---|---|
| 时间 | 两天（2 天）完成 MVP |
| 人员 | 3 人团队 |
| 已确认技术栈 | 后端 Python + FastAPI；数据库 PostgreSQL + pgvector；前端 React 18 + Vite；认证 JWT；Embedding text-embedding-v4；核验 AI mimoV2.5-pro |
| AI 能力边界 | 只用文本 AI，不训练/微调模型，不做图像识别 |
| 数据边界 | 小规模（≥20 条测试记录），不部署独立向量数据库 |
| 演示要求 | 至少演示一条高可信自动待交接、一条冲突转管理员、一个 AI/权限失败场景 |

## 4. 预设假设

| 编号 | 假设 | 如果假设不成立的影响 |
|---|---|---|
| H1 | 两天内可以完成 FastAPI + React + pgvector + JWT 的全栈联调 | 需要降级为规则匹配替代向量匹配 |
| H2 | text-embedding-v4 + mimoV2.5-pro API 在演示时网络可达 | 需要预置结果或本地 fallback |
| H3 | mimoV2.5-pro 能根据隐藏特征生成有效的开放式验证问题 | 需要预置问题模板或拾得者手动补充 |
| H4 | 20 条测试数据足以验证规则阈值 | 阈值可信度需在答辩中说明局限 |
| H5 | 管理员预置账号可满足权限隔离演示 | 不需要完整的 RBAC |

## 5. 非目标（明确不做）

1. **学校统一身份认证** — 仅基础注册登录 + 预置管理员
2. **图像识别 / 图片 AI 匹配** — 整体图片只供人工浏览
3. **独立向量数据库** — 不引入 Milvus/Pinecone，用 pgvector
4. **训练或微调模型** — 只用外部 API
5. **复杂地图和路径推断** — 地点只做预定义层级和文本规则
6. **真实物流 / 线上签收** — 系统只提供联系方式和状态记录
7. **法律意义上的物权判定** — 自动待交接和管理员通过不等于法律证明
8. **多组织 / 多校区 / 复杂管理员协作** — 单系统统一管理员
9. **复杂申诉和追责流程** — 只保留审核结果和审计记录
10. **大规模生产部署验证** — 两天 MVP 使用模拟数据

## 6. 成功标准

| 编号 | 可验证的成功标准 |
|---|---|
| S1 | Web 前端与服务端跑通：失主/拾得者输入 → 公开候选 → 隐藏问答 → 自动/人工路由 → 联系方式授权 → 拾得者交接确认 |
| S2 | 候选页只返回 PUBLIC 数据，MATCH_ONLY/VERIFICATION/PRIVATE 不泄露 |
| S3 | 至少一次高可信自动待交接主路径成功演示 |
| S4 | 至少一次冲突/异常转管理员复核路径成功演示 |
| S5 | 至少一个 AI 失败/权限失败场景有记录和处理 |
| S6 | 所有 AI 结果包含结论、依据、冲突、置信度和不确定性说明 |
| S7 | 审计日志可追溯：输入引用、AI 结果、自动/人工决定、交接状态 |
| S8 | 正常、边界、失败、回归和 E2E 测试证据完整 |
