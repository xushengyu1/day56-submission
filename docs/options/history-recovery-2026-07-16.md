## 二、方案阶段拒绝的顶层方案

### 2.1 拒绝：方案 B — 规则优先 + 最小 AI

**方案描述**：确定性规则做匹配，拾得者手动设置隐藏问题，LLM 仅做核验；前端 Jinja2 SSR。

**拒绝原因**：

1. **前端交互体验一般**：表单提交 + 整页刷新，无实时反馈
2. **隐藏问题由拾得者手动编写**：学习成本高，问题质量参差不齐
3. **Embedding 模型与用户选择不符**：用户确认使用 text-embedding-v4（方案 B 使用 OpenAI text-embedding-3-small）
4. **核验模型与用户选择不符**：用户确认使用 mimoV2.5-pro（方案 B 使用 GPT-4o-mini）

**潜在代价**：

- 失去 SSR 的零构建工具优势
- React 开发成本高于 Jinja2

**隐藏风险**：

- SSR 架构下前后端耦合度高，后续迁移到 SPA 需重写前端

**何时重新考虑**：

- 项目周期 ≤ 1 天
- 团队无 React 经验

---

### 2.2 拒绝：方案 C — LLM 驱动全流程

**方案描述**：匹配、核验、质量检查全部依赖 LLM API；前端 React SPA。

**拒绝原因**：

1. **匹配延迟过高**：每次匹配需调用 LLM，20 条记录对比 = 多次 API 调用
2. **LLM 输出不稳定**：同一输入多次调用可能得到不同分数，难以精确断言测试
3. **外部依赖最重**：匹配 + 核验 + 质量检查三处 LLM 调用
4. **无法利用 pgvector**：已确认的 pgvector 能力被浪费

**潜在代价**：

- 失去 LLM 直接匹配的深度语义理解

**隐藏风险**：

- LLM 匹配的延迟和成本随记录数线性增长

**何时重新考虑**：

- 记录数 < 10 条（LLM 调用次数可控）
- 网络环境极好且 API 预算充足

---

## 三、子决策拒绝的选项

### 3.1 拒绝：Jinja2 SSR 前端

- 用户确认使用 React
- SSR 交互体验差（表单提交 + 整页刷新）
- 前后端耦合，不利于后续扩展

**潜在代价**：

- React 需要 Vite 构建工具、JWT 认证、CORS 配置

### 3.2 拒绝：OpenAI text-embedding-3-small

**拒绝原因**：

- 用户确认使用 text-embedding-v4

**潜在代价**：

- text-embedding-v4 的具体参数（维度、延迟、成本）需验证

### 3.3 拒绝：OpenAI GPT-4o-mini 作为核验模型

**拒绝原因**：

- 用户确认使用 mimoV2.5-pro

**潜在代价**：

- mimoV2.5-pro 的结构化输出能力和 prompt 工程需验证

## 方案 A：向量匹配 + LLM 核验 ✅ 已选

### 核心架构思路

**"双方信息都向量化，pgvector 做召回取 TOP-5，LLM 自动生成隐藏问题并核验回答。"**

- 匹配：失主和拾得者的公开描述均通过 text-embedding-v4 向量化 → pgvector 余弦相似度 + 时间/地点规则评分 → TOP-5
- 隐藏问题：拾得者上传隐藏特征（私密文字描述）→ mimoV2.5-pro 根据特征自动生成开放式验证问题
- 回答核验：失主回答 → mimoV2.5-pro 比对回答与隐藏特征 → 匹配/部分匹配/冲突/无法判断

### 技术选型

| 层级 | 选择 | 理由 |
|---|---|---|
| 前端 | React 18 + Vite | 组件化、热重载、交互体验最佳 |
| 数据访问 | SQLAlchemy ORM + raw SQL for pgvector | ORM 加速 CRUD，pgvector 查询用 raw SQL |
| 认证 | JWT (access + refresh) | 前后端分离标准方案 |
| Embedding | text-embedding-v4 | 双方信息向量化，中文语义理解强 |
| 匹配引擎 | pgvector 余弦相似度 | 向量匹配 → 结合规则 → TOP-5 |
| 问题生成 | mimoV2.5-pro | 根据隐藏特征自动生成开放式问题 |
| 回答核验 | mimoV2.5-pro | 语义比对，结构化输出 |

### 核心业务流程

│ 1. 发布阶段                                                      │
│                                                                  │

│          ──→ 上传隐藏特征（私密描述，如"伞套内侧写有SZY"）          │
│          ──→ 上传整体图片                                         │
│                                                                  │
│   失主 ──→ 填写失物信息（类别/描述/时间/地点）                      │
│                                                                  │
│   系统 ──→ text-embedding-v4 将双方公开描述向量化                   │
│         ──→ 向量存入 PostgreSQL pgvector                           │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│ 2. 匹配阶段                                                      │
│                                                                  │
│   失主发布失物后 ──→ 系统自动触发匹配                              │
│                                                                  │

│         ──→ 结合时间/地点规则评分                                  │

│                                                                  │

│         ──→ 选择要认领的物品                                       │

## 方案 B：规则优先 + 最小 AI（已拒绝）

### 核心架构思路

**"用确定性规则证明系统可靠，用最小 AI 调用完成题面要求。"**

- 匹配：硬规则（类别/类型/状态）+ 规则评分（时间/地点/关键词）
- 隐藏问题：拾得者手动设置问题和标准答案
- 核验：LLM API 语义比对
- 前端：Jinja2 SSR + 原生 JS

### 技术选型

| 层级 | 选择 |
|---|---|
| 前端 | Jinja2 SSR + 原生 HTML/JS/CSS |
| 数据访问 | SQLAlchemy ORM + raw SQL for pgvector |
| 认证 | Session-Cookie + bcrypt |
| Embedding | OpenAI `text-embedding-3-small` |
| 核验 AI | OpenAI GPT-4o-mini |
| 问题质量 | 预置正则规则 |

### 拒绝原因

1. **前端交互体验一般**：表单提交 + 整页刷新
2. **隐藏问题由拾得者手动编写**：学习成本高，问题质量参差不齐
3. **Embedding 模型与用户选择不符**：用户确认使用 text-embedding-v4
4. **核验模型与用户选择不符**：用户确认使用 mimoV2.5-pro

## 方案 C：LLM 驱动全流程（已拒绝）

### 核心架构思路

**"让 AI 做所有语义判断，系统只负责数据流转和状态管理。"**

- 匹配：LLM 直接比较两段描述的语义相似度
- 隐藏问题：LLM 生成
- 核验：LLM 语义比对
- 前端：React SPA

### 技术选型

| 层级 | 选择 |
|---|---|
| 前端 | React 18 + Vite + TailwindCSS |
| 数据访问 | asyncpg 直接 SQL |
| 认证 | JWT (access + refresh) |
| 候选匹配 | LLM 直接比较 |
| 核验 AI | LLM |
| 问题质量 | LLM |

### 拒绝原因

1. **匹配延迟过高**：每次匹配需调用 LLM，20 条记录对比 = 多次 API 调用
2. **LLM 输出不稳定**：同一输入多次调用可能不同分数
3. **外部依赖最重**：匹配 + 核验 + 质量检查三处 LLM 调用
4. **无法利用 pgvector**：已确认的 pgvector 能力被浪费

## 关键取舍说明

### 取舍 1：LLM 自动生成问题 vs 拾得者手动编写

- **选择 LLM 自动生成**：拾得者只需上传隐藏特征（如"伞套内侧写有SZY"），LLM 自动生成开放式问题
- **代价**：拾得者对问题的控制力降低；LLM 生成的问题可能不完全符合拾得者预期
- **缓解**：拾得者可查看生成的问题并确认；隐藏特征的质量是关键输入

### 取舍 2：React SPA vs SSR

- **选择 React SPA**：组件化交互，用户体验最佳
- **代价**：需要 Vite 构建工具、JWT 认证、CORS 配置，开发成本高于 SSR
- **缓解**：Vite 热重载加速开发；JWT 标准方案成熟；前后端分离架构清晰

### 取舍 3：外部 API 依赖 vs 本地模型

- **选择外部 API（text-embedding-v4 + mimoV2.5-pro）**：模型质量最高，无需本地资源
- **代价**：需要网络可达；API 超时需降级处理
- **缓解**：Embedding 超时降级为关键词匹配；核验超时转管理员复核

### 取舍 4：向量匹配 vs LLM 直接匹配

- **选择 pgvector 向量匹配**：利用已确认的 pgvector 能力，匹配延迟低
- **代价**：向量匹配只能捕捉语义相似度，无法像 LLM 那样理解复杂逻辑关系
