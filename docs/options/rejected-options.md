## 二、方案阶段拒绝的顶层方案

### 2.1 拒绝：方案 B — 规则优先 + 最小 AI

**方案描述**：确定性规则做匹配，拾得者手动设置隐藏问题，LLM 仅做核验；前端 Jinja2 SSR。

**拒绝原因**：

1. **前端交互体验一般**：表单提交 + 整页刷新，无实时反馈
2. **隐藏问题由拾得者手动编写**：学习成本高，问题质量参差不齐
3. **Embedding 模型与用户选择不符**：用户确认使用 text-embedding-v4（方案 B 使用 OpenAI text-embedding-3-small）
4. **核验模型与用户选择不符**：用户确认使用 mimoV2.5-pro（方案 B 使用 GPT-4o-mini）

**潜在代价**：

- 失去 SSR 的零构建工具优势
- React 开发成本高于 Jinja2

**隐藏风险**：

- SSR 架构下前后端耦合度高，后续迁移到 SPA 需重写前端

**何时重新考虑**：

- 项目周期 ≤ 1 天
- 团队无 React 经验

---

### 2.2 拒绝：方案 C — LLM 驱动全流程

**方案描述**：匹配、核验、质量检查全部依赖 LLM API；前端 React SPA。

**拒绝原因**：

1. **匹配延迟过高**：每次匹配需调用 LLM，20 条记录对比 = 多次 API 调用
2. **LLM 输出不稳定**：同一输入多次调用可能得到不同分数，难以精确断言测试
3. **外部依赖最重**：匹配 + 核验 + 质量检查三处 LLM 调用
4. **无法利用 pgvector**：已确认的 pgvector 能力被浪费

**潜在代价**：

- 失去 LLM 直接匹配的深度语义理解

**隐藏风险**：

- LLM 匹配的延迟和成本随记录数线性增长

**何时重新考虑**：

- 记录数 < 10 条（LLM 调用次数可控）
- 网络环境极好且 API 预算充足

## 三、子决策拒绝的选项

### 3.1 拒绝：Jinja2 SSR 前端

**拒绝原因**：

- 用户确认使用 React
- SSR 交互体验差（表单提交 + 整页刷新）
- 前后端耦合，不利于后续扩展

**潜在代价**：

- React 需要 Vite 构建工具、JWT 认证、CORS 配置

### 3.2 拒绝：OpenAI text-embedding-3-small

**拒绝原因**：

- 用户确认使用 text-embedding-v4

**潜在代价**：

- text-embedding-v4 的具体参数（维度、延迟、成本）需验证

### 3.3 拒绝：OpenAI GPT-4o-mini 作为核验模型

**拒绝原因**：

- 用户确认使用 mimoV2.5-pro

**潜在代价**：

- mimoV2.5-pro 的结构化输出能力和 prompt 工程需验证

### 3.4 拒绝：拾得者手动设置隐藏问题

**拒绝原因**：

- 用户确认改为 LLM 自动生成
- 降低拾得者编写问题的门槛
- LLM 可生成更规范的开放式问题

**潜在代价**：

- 拾得者对问题的控制力降低
- LLM 生成的问题可能泄露隐藏特征的表述方式

**隐藏风险**：

- 如果 LLM 生成的问题过于直接（如"伞套内侧是否有标记？"），可能帮助冒领者缩小猜测范围
- 需要设计 prompt 确保问题足够开放

### 3.5 拒绝：sentence-transformers 本地 Embedding

**拒绝原因**：

- 用户确认使用 text-embedding-v4（外部 API）
- 本地模型首次加载慢（5-10 秒），内存占用约 500MB

**潜在代价**：

- 引入外部 API 依赖和成本

| 旧决定 | 状态 | 替代原因 | 保留代价/风险 |

| 图片只供人工浏览，不调用视觉模型 | **已替代** | 用户明确要求拾得者上传图片后由多模态模型提取物品名称和特征 | 新方案必须增加原图授权、AI 错误确认和失败降级 |

## 2. 已拒绝的顶层方案

### 2.1 方案 B：OCR/规则优先流水线

- **拒绝的确切原因**：不能完整满足"普通物品上传图片后自动识别名称和特征描述"的 P0 要求；仍需拾得者手工填写普通物品公开信息。
- **放弃它的代价**：失去更窄的隐私边界、更稳定的 OCR 字段和最容易测试的规则链。
- **隐藏风险**：如果通用多模态模型对证件号码识别效果差，最终可能不得不重新引入 OCR，造成返工。
- **何时重新考虑**：用户把普通物品自动提取降为 P1，或禁止 PRIVATE 图片发送通用多模态 API。

### 2.2 方案 C：端到端多模态 LLM

- **拒绝的确切原因**：把精确证件号码、图片、候选和认领判断交给概率模型，无法满足确定性、隐私隔离和可复现测试要求。
- **放弃它的代价**：需要自己实现 HMAC 比对、双状态机、规则路由和脱敏，代码量高于单模型方案。
- **隐藏风险**：混合方案可能出现"模型字段、人工字段、规则字段"版本不一致，需要事务和快照控制。
- **何时重新考虑**：只做无真实敏感数据的概念演示，且不需要自动待交接或精确号码判断。

## 3. 当前拒绝的子选项

| 子选项 | 拒绝原因 | 潜在代价 | 隐藏风险 |
|---|---|---|---|
| 模型提取后直接发布 | 号码/名称误识别会成为正式事实 | 多一个人工确认页面 | 用户可能不认真核对，需要明确确认交互 |
| 完整证件号码作为数据库明文字段 | 泄露面过大，普通查询/日志容易暴露 | HMAC 后无法直接恢复号码 | 号码规范化错误会导致不可匹配 |
| 使用普通 SHA-256 保存证件号码 | 固定格式号码可能被离线枚举 | HMAC 需要服务端密钥管理 | 密钥丢失后历史号码无法重新计算 |
| 把完整号码放入 embedding 或 LLM prompt | 不需要语义能力，且扩大外部处理范围 | 需单独实现精确比对服务 | 错误日志、模型供应商记录可能泄露 |
| 公开身份证件原图 | 即使掩码文本安全，图片仍泄露完整信息 | 需要生成并校验脱敏副本 | 自动遮挡漏区会造成高风险泄露 |
| 号码不匹配时提示错误位数 | 会帮助攻击者逐位枚举 | 只能提供通用提示，用户体验较弱 | 错误输入用户可能不知道如何纠正 |
| 身份证件匹配后直接标记已认领 | 绕过线下交接和拾得者责任 | 多保留一个待交接状态 | 拾得者忘记确认会留下未完成状态 |
| 为 MVP 建 HNSW/IVFFlat | 小数据量没有证据证明需要近似索引，增加召回误差和初始化成本 | 精确检索扩展性有限 | 数据量增长后需重新评估 |

## 4. 明确保留但本轮不扩展的选项

1. 失主可选图片：先作为 PRIVATE 支持材料，不自动提取。
2. 多证件类型：MVP 已确认仅支持居民身份证，避免一次实现多套号码规则。
3. 本地多模态模型：作为禁止外部传图时的备选，不在两天 MVP 默认部署。
4. 证件真伪验证、公安接口和校园统一身份认证：明确非目标。
