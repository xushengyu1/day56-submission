# 取舍矩阵

**文档版本：** V4.0  
**更新日期：** 2026-07-16  
**评分状态：** 设计阶段证据评分，尚未用运行原型校准

## 1. 评分方法

- 每项 1～5 分：1=明显不满足，3=部分满足/有显著代价，5=高度满足且风险可控。
- 加权总分 = `Σ(单项分 × 权重)`，满分 5。
- 权重来自 PRD V0.8 的两天 MVP、隐私和可验证性约束，不代表生产系统长期权重。

| 维度 | 权重 | 可核查依据 |
|---|---:|---|
| 新需求覆盖度 | 25% | 是否同时覆盖图片自动提取、可修改、身份证件/其他分流 |
| 隐私与防冒领 | 20% | 完整号码/原图进入哪些组件，是否确定性核验、是否可限流 |
| 两天可交付性 | 20% | 新组件数量、状态数量、失败降级和团队现有 Python/FastAPI 约束 |
| 可测试与可解释 | 15% | 核心判断是否可重复、能否固定输入输出、能否指出触发规则 |
| 失败隔离能力 | 10% | 单一模型故障是否摧毁全流程，是否有手工/规则降级 |
| 可维护性 | 10% | 模型替换、证件类型扩展和规则修改的影响范围 |

## 2. 方案评分

| 方案 | 需求覆盖 25% | 隐私安全 20% | 两天交付 20% | 可测试解释 15% | 失败隔离 10% | 可维护 10% | 加权总分 |
|---|---:|---:|---:|---:|---:|---:|---:|
| A：受控多模态 + 人工确认 + 分类型核验 | 5 | 4 | 4 | 5 | 4 | 4 | **4.40** |
| B：OCR/规则优先流水线 | 3 | 5 | 3 | 5 | 5 | 4 | **4.00** |
| C：端到端多模态 LLM | 5 | 2 | 4 | 2 | 2 | 3 | **3.25** |

计算示例：方案 A = `5×0.25 + 4×0.20 + 4×0.20 + 5×0.15 + 4×0.10 + 4×0.10 = 4.40`。

## 3. 逐项评分证据

### 3.1 方案 A

| 维度 | 分数 | 证据与推理 |
|---|---:|---|
| 需求覆盖 | 5 | 直接覆盖用户要求的图片后自动识别、拾得者修改、身份证件号码核验、其他物品隐藏特征 |
| 隐私安全 | 4 | 号码最终由 HMAC 精确比对且不进 LLM；扣 1 分因为 PRIVATE 原图仍需发送多模态 API |
| 两天交付 | 4 | 复用现有 FastAPI/pgvector/LLM；新增图片双版本和双状态分支，存在联调成本 |
| 可测试解释 | 5 | AI 提取与人工确认可分开断言；号码精确匹配完全确定；其他物品保留结构化评分 |
| 失败隔离 | 4 | 模型失败可手工填写；扣 1 分因为发布体验仍依赖外部 API 的正常返回或降级 UI |
| 可维护 | 4 | 模型适配器、号码核验和其他物品核验分层；新增证件类型仍需规范化/掩码规则 |

### 3.2 方案 B

| 维度 | 分数 | 证据与推理 |
|---|---:|---|
| 需求覆盖 | 3 | 能处理身份证件号码，但不能完整满足普通物品图片自动生成名称和特征 |
| 隐私安全 | 5 | 证件 OCR 和规则可在更窄的数据范围运行，普通物品不向通用多模态模型发图 |
| 两天交付 | 3 | 需要 OCR、证件规则、普通物品手工表单和规则候选四套逻辑，且偏离现有模型链 |
| 可测试解释 | 5 | OCR 字段、格式校验、规则评分和精确比对均可固定输入输出 |
| 失败隔离 | 5 | OCR 失败不影响普通物品手工流程；规则服务可独立降级 |
| 可维护 | 4 | 规则明确；证件种类扩展需要持续维护版式和号码格式 |

### 3.3 方案 C

| 维度 | 分数 | 证据与推理 |
|---|---:|---|
| 需求覆盖 | 5 | 模型可表面覆盖图片、文本、候选和核验全部环节 |
| 隐私安全 | 2 | 需要把原图、完整号码和隐藏信息交给同一模型，最小化和隔离最弱 |
| 两天交付 | 4 | 业务代码较少；但 prompt、结构校验和异常重试仍需要实现 |
| 可测试解释 | 2 | 生成式结论不稳定，精确号码不应使用概率判断；难证明具体触发规则 |
| 失败隔离 | 2 | 模型超时或限流会同时影响发布、匹配和认领 |
| 可维护 | 3 | 接口统一，但 prompt 变化可能影响全部业务阶段，回归面大 |

## 4. 评分依据来源

| 证据 | 支持的判断 |
|---|---|
| [MiMo 图片理解官方文档](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/multimodal-understanding/image-understanding) | 模型可接收图片并做描述/分类，支持方案 A/C；文档不承诺证件号码零错误，因此不能取消人工确认 |
| [MiMo API 集成 FAQ](https://mimo.mi.com/docs/en-US/quick-start/faq/api-integration) | 官方建议合理超时与指数退避；支持把外部 API 失败列为方案风险 |
| [FastAPI UploadFile](https://fastapi.tiangolo.com/tutorial/request-files/) | 现有 FastAPI 栈可直接接收 multipart 图片，降低方案 A/B 接入成本 |
| [pgvector 官方 README](https://github.com/pgvector/pgvector) | PostgreSQL 可同时保存业务数据和向量；默认精确检索适合小规模 MVP |
| [PostgreSQL pgcrypto](https://www.postgresql.org/docs/current/pgcrypto.html) | 支持 HMAC；官方安全说明支持应用层最小化处理和 TLS 要求 |
| PRD V0.8 | 身份证件/其他双分支、拾得者确认、完整号码不公开是硬约束 |

## 5. 敏感性分析

1. 如果 Q3 确认失主图片也必须自动识别，方案 A 两天交付分从 4 降为 3，总分变为 4.20，仍高于 B。
2. 如果 PO 将普通物品多模态提取降为非目标，方案 B 的需求覆盖可从 3 升到 5，总分变为 4.50，可能反超 A。
3. 如果不允许 PRIVATE 图片发送外部 API，方案 A 必须改成本地模型或 B，当前推荐失效。
4. 如果身份证件范围扩到护照/驾驶证/校园卡，A/B 的交付分都需重新评分，不能沿用 4.40/4.00。

## 6. 排名结论

基于当前证据，方案 A（4.40）已被用户接受；方案 B（4.00）和 C（3.25）已拒绝。Q1～Q15 已确认，评分的决策作用已经完成；最小 spike 仍用于校准实现风险，不改变已发生的方案选择，若验证失败则按变更流程重新评审。
