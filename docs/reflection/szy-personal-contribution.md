## 3. 产品判断与 PRD 迭代贡献

### 3.1 把题目从“信息展示”收敛为“可验证认领闭环”

我没有把系统定义为一个普通的失物招领信息墙，而是把核心问题拆成四层：

- 公开信息只能帮助失主发现候选，不能证明所有权；
- AI 匹配只负责生成 Top 5 和解释，不直接确认归属；
- 普通物品通过未公开的隐藏特征核验；
- 身份证件通过确定性的号码核验；异常情况统一进入管理员复核。

这一判断形成了“发布 → 候选 → 分类型核验 → 自动/人工路由 → 线下交接 → 审计追溯”的核心闭环。证据见 [PRD 产品定义](../../prd.md)、[PRD 目标与非目标](../../prd.md) 和 [问题诊断](../diagnosis/problem-diagnosis.md)。

### 3.2 明确角色与责任边界

我提出并确认系统只有三类业务/权限角色：

- **失主**：发布失物、查看 Top 5、发起认领、回答隐藏问题或输入身份证号、主动申请复核；
- **拾得者**：发布招领、确认 AI 草稿、填写隐藏特征、保管实物、完成线下交接后更新状态；
- **管理员**：处理多人认领、核验异常、身份证异常和失主主动复核，并填写决定理由。

同时明确 AI 是能力模块，不是责任主体；管理员不保管实物，系统也不能在真实交接前自动标记“已认领”。证据见 [PRD 角色与权限边界](../../prd.md) 和 [PRD 迭代日志 P-01～P-04](../diagnosis/prd-iteration-log.md)。

### 3.3 提出身份证件与普通物品双核验策略

我提出物品只在认领核验阶段分为两类，而不是复制两套完整系统：

- 两类物品共享注册、发布、候选匹配、管理员复核、交接和审计流程；
- `OTHER` 使用隐藏问题和 AI 语义核验；
- `IDENTITY_DOCUMENT` 不要求隐藏特征，使用完整号码做确定性核验；
- 身份证候选页只显示掩码和脱敏图片；失败不提示具体错误位；异常和重复记录转管理员；
- 核验成功只进入 `PENDING_HANDOFF`，不能直接进入 `CLAIMED`。

这一设计避免了“同一主流程复制两遍”，同时把概率判断和确定性判断分开。证据见 [PRD 7.6 分类型认领核验](../../prd.md)、[PRD 迭代日志 P-31～P-43](../diagnosis/prd-iteration-log.md) 和 [个人 AI 日志记录 23～25](../../szy-ai-log.md)。

### 3.4 持续迭代而不是一次性生成 PRD

我推动 PRD 经历了多轮有依据的变化：

1. 从初始失物招领闭环，修正为失主/拾得者/管理员三角色；
2. 删除失物招领处和管理员保管实物假设；
3. 加入注册登录、Top 5、隐藏问题和人工复核；
4. 将 MySQL 替换为 PostgreSQL + pgvector；
5. 合并重复的颜色/外观分与描述语义分，形成 `50 + 20 + 20 + 10`；
6. 根据新需求加入图片识别草稿和身份证分支；
7. 当文档被过度简化时，否决全量重写，恢复详细基线后做最小增量；
8. 将复杂功能架构图收敛成角色核心功能、AI 能力、安全防冒领和系统支撑四层表达。

这体现了我对“需求变更必须产生版本、理由、影响范围和验证要求”的工程化理解。完整证据见 [PRD 迭代日志](../diagnosis/prd-iteration-log.md)、[决策日志](../collaboration/decision-log.md) 和 [个人 AI 日志](../../szy-ai-log.md)。

## 4. 后端架构思路与贡献

> 本节是我的重点贡献。当前证据证明的是“后端架构、规则和开发方案由我主导设计”，不等同于“后端代码已由我实现”。

### 4.1 先划分责任，再选择技术

我将系统拆成以下后端领域能力，而不是按页面堆接口：

| 后端模块 | 设计职责 | 我的关键判断 |
|---|---|---|
| Auth / RBAC | 注册、登录、用户/管理员授权、资源归属 | 前端路由守卫只改善体验，服务端必须再次鉴权 |
| Item Service | 失物/招领草稿、人工确认、发布、取消、关闭 | 正式公开字段只能来自拾得者确认后的快照 |
| Image Service | 原图保存、格式校验、脱敏副本、访问授权 | PRIVATE 原图与 PUBLIC 脱敏副本物理和权限分离 |
| Multimodal Adapter | 图片提取、问题生成、答案核验的统一模型接口 | 业务层不直接依赖供应商 SDK；非法结构必须被校验拒绝 |
| Candidate Matching | 硬过滤、向量相似度、时间/地点/完整度评分、Top 5 | 候选分只排序，不证明所有权，不触发直接交接 |
| ID Verification | 号码规范化、校验、HMAC、掩码、次数限制 | 确定性相等问题不能交给 LLM 判断 |
| Other Verification | 隐藏问题生成、回答核验、低置信路由 | AI 只能输出受控枚举和置信度；失败转人工，不自动放行 |
| Admin Review | 五类异常队列、确认/驳回、理由与幂等 | 管理员有复核权，不默认拥有全部 PRIVATE 数据 |
| Audit Service | 业务事件、模型事件、版本和安全时间线 | 审计事件只追加，不能被业务接口覆盖或删除 |

详细证据见 [端到端设计 8.1～8.9](../design/end-to-end-system-design.md) 和 [dev.md 模块开发规范](../../dev.md)。

### 4.2 将概率型 AI 与确定性规则隔离

这是我在后端设计中最重要的判断之一：

- 多模态模型只提取“草稿”，不能直接形成业务事实；
- embedding 只用于公开文本相似度和候选排序；
- 普通物品核验允许 AI 处理语义同义表达，但低置信、冲突、输出异常必须转人工；
- 身份证号码相等属于确定性规则，使用规范化、HMAC-SHA256 和常量时间比较，不调用 LLM；
- AI 失败不能伪造结果，系统必须保留手工填写、规则降级或管理员复核路径。

这使系统既能使用 AI 的模糊理解能力，又不会把敏感数据和所有权判断交给概率模型。证据见 [PRD 产品原则](../../prd.md)、[design_option 方案 A](../../design_option.md) 和 [详细设计 8.3、8.6、8.7](../design/end-to-end-system-design.md)。

### 4.3 数据架构：结构化数据、向量和证据放在同一事务边界中考虑

我确认采用 PostgreSQL + pgvector，而不是 MySQL 加独立向量库，原因是两天 MVP 更需要部署简单、数据一致和证据可追溯。我的设计包括：

- 常规表保存用户、记录、候选、认领、管理员复核和审计事件；
- pgvector 保存拾得者确认后的公开文本向量；
- 一个已确认物品记录对应一个检索单元，避免一个物品被切成多个向量造成重复候选；
- 小数据量 MVP 使用精确余弦查询，不提前引入 ANN 索引；
- 外部模型调用不占用数据库事务，先保存任务，模型返回后基于版本条件更新，避免旧结果覆盖用户新修改；
- 候选和核验结果保存规则版本、模型版本、输入快照哈希和结果代码。

证据见 [PRD 技术栈](../../prd.md)、[详细设计数据表与不变量](../design/end-to-end-system-design.md)、[详细设计数据库与事务](../design/end-to-end-system-design.md) 和 [个人 AI 日志记录 10](../../szy-ai-log.md)。

### 4.4 把业务规则写成可测试的不变量和状态机

我没有把流程只画成页面跳转，而是定义了实现必须遵守的数据不变量：

- 身份证招领必须存在号码 HMAC，且不能存在有效隐藏问题集；
- 普通物品必须存在 2～3 个已确认问题，且不能保存身份证 HMAC；
- PUBLIC 图片只能引用已确认的脱敏副本；
- 同一账号对同一身份证候选最多尝试 2 次；
- 同一 HMAC 对应多条活动招领时禁止自动进入待交接；
- 只有 `PENDING_HANDOFF` 才能展示联系方式；
- 正常路径只有拾得者能够在真实交接后触发 `CLAIMED`；
- 未匹配复核只能推荐候选，不能跳过认领核验直接放行。

这些规则直接转化为后端单元、集成、权限和 E2E 测试目标。证据见 [详细设计 6.3 数据不变量](../design/end-to-end-system-design.md)、[dev.md TDD 与质量门](../../dev.md) 和 [验证案例](../validation/cases-and-results.md)。

### 4.5 安全设计不是前端隐藏，而是服务端用途隔离

四级数据分类由徐胜宇提出；我在文档和架构层将其落实为：

- 候选响应使用用途专属 DTO，只返回 PUBLIC；
- MATCH_ONLY 可参与内部匹配，但不能把坐标、向量和模型特征原样返回；
- VERIFICATION 只在隔离核验服务和必要复核中使用，答案不能返回失主；
- PRIVATE 默认不进入候选、LLM、解释和普通日志；
- 管理员也不因为角色身份自动看到完整号码和原图；
- 联系方式只在待交接且已授权后展示。

我的贡献是把团队提出的数据分级思想转化为可落地的接口、数据表、日志、AI 输入和测试规则。证据见 [PRD 第 5 章](../../prd.md)、[详细设计 6～8 章](../design/end-to-end-system-design.md) 和 [前端安全测试](../validation/test-strategy.md)。

## 5. 技术方案与工程规划贡献

### 5.1 三种本质方案比较

我没有直接采用 AI 给出的第一套方案，而是组织了三条本质不同的路线：

- 受控多模态 + 人工确认 + 分类型核验；
- OCR/确定性规则优先；
- 端到端多模态模型决策。

我最终选择方案 A，并明确拒绝“让 LLM 比较完整身份证号码”和“模型结果不经确认直接发布”。选择依据包括需求覆盖、可解释性、敏感数据风险、两天可交付性、失败降级和证据链。证据见 [design_option.md](../../design_option.md)、[方案选项](../options/solution-options.md)、[取舍矩阵](../options/tradeoff-matrix.md) 和 [拒绝方案](../options/rejected-options.md)。

### 5.2 将设计转换为开发规则，而不是直接让 AI 生成代码

Design Review 后，我继续形成 `dev.md`，把设计约束转换为：

- 依赖和技术版本；
- 服务模块边界；
- 数据迁移、状态规则和权限要求；
- 模型适配器与 mock 边界；

- 每个任务必须保存命令、结果、截图、提交和未解决限制。

我还明确规定：时间不足时可以把真实模型降级为 mock，可以放弃次要视觉优化，但不能降级四级权限、号码保护、状态机和证据真实性。证据见 [dev.md](../../dev.md) 和 [任务拆分](../../task.md)。

## 6. 文档设计与证据工程贡献

### 6.1 建立从问题到验证的文档链

我负责记录和维护以下主线文档：

```text
问题诊断
→ 澄清问题
→ PRD 与多轮迭代
→ 三方案比较与取舍矩阵
→ 最终建议与 ADR
→ 端到端详细设计
→ Design Review
→ dev.md 与 task.md
→ 测试策略、案例和执行结果
→ AI 日志、会议、决策、复盘与答辩证据
```

这套结构的目的不是增加文档数量，而是使每个结论都能回答：为什么提出、比较过什么、谁决定、AI 建议是否采纳、如何验证、当前是否真实完成。

### 6.2 文档即工程契约

我的文档设计具有以下工程特征：

1. **需求可追溯**：使用 FR、决策编号、任务编号和测试编号建立引用关系。
2. **版本可追溯**：旧决定被替代时保留原因，不把历史事实静默删除。
3. **真假边界清楚**：计划、设计、Mock、真实实现和实际测试分别标注。
4. **失败路径优先**：文档不仅描述正向流程，也明确超时、低置信、重复号码、多人认领和权限泄露场景。
5. **角色与技术端分离**：失主/拾得者/管理员是用户角色，React 前端/FastAPI 服务端才是技术端。
6. **AI 建议可审查**：记录目的、输入、建议、人工判断和验证，保留采纳、修改和拒绝证据。

证据见 [个人 AI 日志](../../szy-ai-log.md)、[AI 协作日志](../ai/ai-collaboration-log.md)、[决策日志](../collaboration/decision-log.md)、[Review 记录](../validation/review-record.md) 和各目录历史恢复账本。

### 6.3 发现文档覆盖问题后建立追加式治理

当过程文档因多轮迭代出现旧记录被覆盖的问题时，我要求过程文档改为“只追加、不覆盖”。随后通过 Git 提交链恢复了 38 个唯一历史快照，并采用“错误条目保留 + 追加更正”的方式维护证据。

这一处理体现了我对过程证据可信度的重视：Git 不只是代码版本工具，也是需求、决策和 AI 协作的审计来源。证据见各过程目录的 `history-recovery-2026-07-16.md`、[AI-015](../ai/ai-collaboration-log.md) 和 [D-APPEND-001](../collaboration/decision-log.md)。

### 7.3 将后端安全思想映射到前端交互

我在前端实现中保留了后端架构的核心边界：

- access/refresh token 只放内存，不写 localStorage；
- 普通用户和管理员使用独立路由布局；
- 身份证候选只展示掩码号码，输入不足 18 位不能提交；
- 普通物品只展示开放式问题，不显示隐藏答案；
- 候选卡展示匹配点、冲突点和保留原因，而不是只展示总分；
- 联系方式只在待交接进度中展示；
- 管理员决定必须填写理由。

这些不是纯视觉效果，而是把权限、状态机和防冒领规则转成用户可以理解和测试的界面行为。

## 8. AI Native 工程化思维体现

### 8.1 把 AI 当作协作能力，不当作决策主体

我使用 AI 进行需求澄清、方案对比、架构反思、文档与代码实现、测试设计和 Review，但最终范围、风险接受和阶段确认由我判断。典型证据包括：

- 拒绝 AI 的多页面、大范围初稿，收敛为最小闭环；
- 拒绝 Jinja2 SSR，选择 React + Vite；
- 替换 AI 建议的模型选型；
- 拒绝让 AI 直接比较身份证号；
- 拒绝 V2.0/12 Tasks 的全量简化；
- 拒绝过度复杂的架构图，改为角色化四层表达。

### 8.2 Human-in-the-loop 不是口号，而是状态与数据设计

我把“人工确认”落实为具体工程节点：

- 多模态识别结果只保存为草稿；
- 拾得者必须确认名称、描述、类型和证件号码；
- 正式字段只来源于 `confirmed_snapshot`；
- 低置信、冲突、重复记录和多人认领进入管理员队列；
- 管理员决定必须附理由；
- 实际交接只能由拾得者最终确认。

### 8.3 用结构化契约约束 AI

我要求模型输出固定 JSON、受控枚举、置信度、错误代码和模型版本，并通过 Pydantic 校验。非法 JSON、缺字段、低置信或超时不能直接生效。业务代码通过适配器调用模型，不直接依赖供应商响应格式。

### 8.4 设计时同时考虑正常、失败、降级和证据

每个 AI 能力都配套失败路径：

- 图片识别失败 → 保存草稿并手工填写；
- embedding 失败 → 标记待重试或规则降级，不能自动待交接；
- 核验 AI 失败/低置信 → 管理员复核；
- 脱敏失败 → 不公开原图；
- 输出异常 → 结构校验拒绝；
- 所有过程保存模型版本、输入快照和结果代码。

### 8.5 形成“需求—设计—代码—测试—证据”的闭环

我的 AI Native 实践不是只用 AI 生成代码，而是把 AI 放入完整软件工程流程：

```text
用户反馈
→ AI 帮助澄清和生成备选
→ 人工判断、修改或拒绝
→ 写入 PRD/ADR/设计
→ 转为开发任务和测试断言
→ 执行测试并保存证据
→ Review 结果反向更新文档
```

## 10. 当前边界与不能过度声称的内容

1. **后端贡献目前主要是架构和开发规划，不是后端代码实现。** 后端 HMAC、事务、状态机、AI 适配器和真实 API 仍需以代码和测试证明。
2. **前端当前使用 Mock API。** 已证明页面、组件行为和生产构建，但尚未证明与真实 FastAPI/PostgreSQL 的端到端联调。
3. **真实多模态、embedding 和核验模型效果尚未验证。** 不能声称真实识别准确率或生产安全性。
4. **前端目录目前尚未纳入 Git 跟踪。** 代码和测试已存在且可运行，但答辩前应提交到个人分支/主仓库，以形成提交级个人贡献证据。
5. **当前工作区中的部分 SVG 设计原型被标记为删除。** 本文使用已跟踪的 `prototype/ui` HTML 页面作为 UI 设计证据；如答辩需要 SVG，应先确认恢复或替代方案。

## 11. 答辩个人陈述参考

我在项目中主要负责需求、系统架构、文档证据和前端实现。产品层面，我提出把用户流程分为失主、拾得者和管理员三类任务，并进一步提出身份证件与其他物品采用不同核验方式：普通物品回答隐藏问题，身份证由服务端进行确定性号码核验，AI 不直接判断号码是否相等。架构层面，我重点解决了 AI 能力和业务责任的边界：多模态模型只生成草稿，拾得者确认后才进入正式数据；候选分只用于 Top 5 排序，不能证明所有权；低置信、冲突和多人认领统一转管理员。四级数据分类由徐胜宇提出，我负责把它落实到 PRD、DTO、AI 输入、日志和测试设计中；图片识别想法来自黄孝梁，最终边界和执行方案由我与徐胜宇共同决定。我还独立完成了从 14 张 UI 设计稿到 React 前端实现的工作，本轮 46 个组件测试全部通过，生产构建成功。整个过程中，我没有直接照搬 AI 输出，而是持续记录采纳、修改和拒绝理由，使需求、方案、设计、代码和证据能够互相追溯。
